# 디지털 트윈 연동

대시보드의 Three.js 화면은 로그인한 센터의 저장된 관측을 시간순으로 재생한다.
실제 차량 위치·적재 기록을 추적하는 화면은 아니다. 현재 재고를 시작점으로 박스 선택과
트럭 적재를 브라우저에서 계산하며 DB 재고·발주 상태를 변경하지 않는다.

## 사용 방법

1. 대시보드를 열면 치수 자료가 있는 마지막 날짜의 최대 300건을 불러온다.
2. 기간과 최대 건수를 정하고 `구간 불러오기`를 누른다. 최대 20,000건이다.
3. `한 건`, `재생`, `결과로 건너뛰기`로 진행하고 상자·트럭·호수 통계를 선택해 상세를 본다.
4. `비교 시뮬레이션`에서 승인된 신규 규격 제안서를 선택하고 구간을 불러온다.
   기존 라인과 제안 라인에 같은 물품을 같은 순서로 투입한다.

## 조회 계약

모든 경로의 접두사는 `/api/v1/warehouses/{warehouseId}`이며 기존 로그인 세션과 센터 권한을 적용한다.

| API | 사용 데이터 |
| --- | --- |
| `GET /simulation-state?limit=1&includeRange=true` | 전체·치수 관측의 최초/최종 시각과 건수 `availableRange` |
| `GET /simulation-state?from=...&to=...&limit=500` | 지정 구간 관측과 치수, 시각·이벤트 ID 오름차순 |
| `GET /box-stocks?active=true` | 박스 내부 치수(mm), 현재 재고, 단가 |
| `GET /procurement-proposals` | 센터의 승인된 AI 제안 목록(최근 100건), 신규 규격 여부 |
| `GET /procurement-proposals/{id}` | 신규 규격, 승인 수량, 분석 기간 |
| `GET /products/{id}` | 상세 패널의 상품 원본 |

`from`과 `to`는 함께 지정하는 ISO 8601 시각이며 양 끝을 포함한다. 화면 입력은 한국 시각이다.
응답의 `hasMore`가 참이면 `nextCursor.observedAt`, `nextCursor.eventId`를 각각
`afterObservedAt`, `afterEventId`로 보내 다음 페이지를 받는다. 커서는 두 값을 함께 지정하며
이전 마지막 행을 제외하므로 같은 시각에 500건 이상 있어도 누락하지 않는다.
페이지당 `limit`은 1~500이다. 기간을 생략한 기존 최근 관측 조회 방식도 유지한다.
기간 역전·한쪽만 있는 기간/커서·구간 밖 커서는 400으로 거절한다.

관측의 `measurement`는 `widthMm`, `depthMm`, `heightMm`, `dlStatus`, `sizeType`,
`latencyMs`, `measuredAt`, `failureReason`, `source`를 포함한다.
신규 결과의 `source=WORKER`는 `item_event.measurement`에서 읽는다.
기존 평가 자료의 `source=IMPORTED_SAMPLE`는 `dl_measurement_sample`에서 이벤트 ID로 연결하며
cm를 mm로 변환한다. 두 자료가 있으면 신규 결과를 우선한다.
`sizeType=measured`는 식별된 상품의 등록 치수이므로 화면에서 `DL 등록 치수`로 표시한다.
미식별 치수는 추정으로 구분하며, 유효한 DL 치수가 없을 때만 상품의 라벨 치수를 사용한다.

## 비교 계산의 기준

신규 규격은 제안서의 승인 수량을 가상 재고로 사용한다. 발주 초안 작성으로 같은 규격이 이미
등록됐더라도 기존 라인에서는 제외하고 제안 라인에 한 번만 추가한다.
새 제안서는 저장된 `analysisPeriod`를 사용한다. 이전 제안서는 입력 기준일 이전 90일을 사용하고
관측이 존재하는 기간과 겹치는 부분을 기본 구간으로 정한다. 사용자가 구간을 변경할 수 있다.

회전해 들어가는 재고 보유 박스 중 충전율이 가장 높은 규격을 고른다.
트럭은 2,800×1,600×1,600mm의 고정 적재함과 기존 화면의 적재 규칙을 사용한다.
치수 없는 관측은 포장 계산에서 제외하며, 박스가 없거나 적재함에 들어가지 않는 물품도 구분한다.
치수·현재 재고·처리 순서·단순 적재 규칙에 따른 시뮬레이션이므로 실제 운행 대수나 절감액을 보장하지 않는다.
비교 구간이 제안서 분석 기간과 다를 수 있고, 대시보드의 월간 비용 추정과도 계산 기준이 다르다.
두 라인의 포장 가능 건수도 함께 표시한다. 신규 규격 덕분에 더 많은 물품을 포장하는 경우에는
트럭 대수만으로 절감 효과를 비교할 수 없다.

## 검증

루트 `digital-twin-check`는 실제 로그인 API와 복원 DB를 읽어 1,200건의 페이지 순서·중복·단위 변환,
잘못된 요청의 400 응답, 승인 제안서 조회를 검사한다.
`node scripts/check-digital-twin-packing.mjs`는 같은 자료로 실제 포장 함수를 실행하고
신규 규격 사용 및 입력 재고 불변을 검사한다. 보고서는 루트 `.local-data/reports`에 저장한다.
클라이언트 테스트는 같은 시각의 500건 초과 페이지, 취소, 중복 규격, 잘못된 치수와 구간 설정을 다룬다.
서버의 선택 조회 테스트 및 PostgreSQL/Kafka 통합 테스트에서 신규 결과 치수 저장도 확인했다.
